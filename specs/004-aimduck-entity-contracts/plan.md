# Implementation Plan: Contratos claros das entidades Aimduck

**Branch**: `master` (feature: `004-aimduck-entity-contracts`) | **Date**: 2026-10-12 | **Spec**: [spec.md](./spec.md)

## Summary

Clarify the Aimduck sample's entity boundaries by grouping shared types into OGS, admission/transport, and game-domain contracts; define the client/server gameplay message and recipient-specific room snapshot as explicit, validated shapes; and align the sample's entity catalog, interface labels, and tests. Keep the change local to the sample: do not add OGS protocol requirements or alter OGS endpoint semantics.

## Technical Context

**Language/Version**: TypeScript 5.8.2; Node.js >=22 (Aimduck workspace)

**Primary Dependencies**: Zod 3.24.2, React 18.3.1, Vite 6.4.4, Fastify 5, `ws` 8, Phaser 3.88.2. No new dependencies are planned.

**Storage**: In-memory room, lobby, and match state; no persistence changes.

**Testing**: Vitest unit/integration projects and Playwright browser tests. Target focused entity design-system and room gameplay contract tests, then workspace typecheck and relevant tests.

**Target Platform**: Local browser-playable Aimduck sample; Node.js room and Discovery services.

**Project Type**: TypeScript monorepo sample with shared package, browser client, Discovery service, room service, and tests under `samples/aimduck/`.

**Performance Goals**: Preserve current gameplay cadence and room message behavior; no new performance target is introduced by this contract-clarity feature.

**Constraints**:

- Entity definitions and the runtime message validator must describe the same public shapes; avoid generic `Record<string, unknown>` for known gameplay message payloads.
- Distinguish room operational state from Aimduck match phase in names, types, snapshot groups, and UI.
- Keep recipient-only state separate from the public roster and simulation state; never include access tokens, join tickets, private keys, or derived session keys in snapshots.
- Keep OGS concepts descriptive/local. Any normative protocol gap or change is outside this feature.
- Preserve existing schema version `1` unless evidence shows an incompatible sample-only contract change is unavoidable; do not imply version 1 is a normative OGS version.

**Scale/Scope**: One sample, its shared types and client/server consumers, focused tests, and directly related sample documentation. No production deployment or general OGS SDK work.

## Design Decisions

1. **Classify by ownership, not by where a type happens to be used.** OGS identity/discovery/room-instance concepts, admission/transport contexts, and Aimduck game entities will be separately identifiable. A GameRoom hosted by a RoomInstance remains game-domain state; the two room operational/game phases remain distinct.
2. **Make the wire contract explicit and shared.** Use strict, discriminated message schemas with inferred TypeScript types for the known message variants and payload fields. Preserve genuinely dynamic maps only where the domain requires them, such as scores keyed by player identity or per-player outcomes.
3. **Make snapshot visibility intentional.** The wire projection's `game` group contains phase, seats, round, scoreboard, and game revision, but not participant sessions. Keep the authenticated recipient's session in `me` and the remaining participant sessions in `others`; the client MUST NOT infer recipient privacy from filtering a shared, all-player session list. `server.roomId` references the OGS RoomInstance, while `game.phase` is Aimduck-only. Simulation remains under `arena`. Do not mistake a display/profile field for an admission credential.
4. **Preserve integration behavior.** Keep authentication, resolution, handshake, gameplay rules, and transport operation unchanged. Add or update focused tests to show that server-produced messages conform to the same validated contract consumed by the client.
5. **Update sample-facing explanations.** Align the sample README, public Aimduck page, entity-oriented UI labels, and focused tests with the same names and ownership categories. Record the Principle VI documentation/harness review.
