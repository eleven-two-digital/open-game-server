## 4. Lacunas e Recursos Faltantes (Sugestões de Evolução)

### 4.1. Paginação e Cursor na Listagem de Salas

> [!IMPORTANT]
> O endpoint `GET /v1/rooms` não define nenhum mecanismo de paginação. Em cenários com centenas ou milhares de salas ativas, a resposta pode ser gigantesca e causar timeout.

**Sugestão:** Adotar paginação por cursor (`?cursor=<opaque_token>&limit=50`) com o campo `next_cursor` na resposta. Isso é mais eficiente que offset/page em catálogos dinâmicos.

### 4.2. Rate Limiting por Player ID / IP

A especificação não menciona rate limiting nos endpoints do DNS. Sem isso, um cliente malicioso pode fazer flood de `GET /v1/rooms` ou `POST /v1/rooms/resolve`.

**Sugestão:** Definir uma regra de negócio `RN-DISC-10` para rate limiting por `player_id` (extraído do JWT) e/ou por IP, retornando `429 Too Many Requests` com header `Retry-After`.

### 4.3. Versionamento de API explícito no Well-Known

O campo `spec_version` no `/.well-known/game-dns` indica a versão da especificação, mas **não há campo `api_version`** para indicar a versão da API REST em si (ex: `v1`, `v2`). Quando endpoints evoluírem para `v2`, o cliente precisa saber qual versão a instância suporta.

**Sugestão:** Incluir `"api_versions": ["v1"]` no Well-Known.

### 4.4. Status da Sala na Listagem (`GET /v1/rooms`)

O documento não define explicitamente quais campos o endpoint `GET /v1/rooms` retorna por sala. É importante especificar ao menos um schema mínimo de resposta:

**Sugestão de campos mínimos:**
```json
{
  "rooms": [
    {
      "masked_token": "tok_abc123",
      "tags": { "game_mode": "5v5", "map": "desert_01" },
      "region": "sa-east-1",
      "ping_host": "ping.sa-east-1.mygame.com",
      "current_players": 4,
      "max_players": 10,
      "status": "ACTIVE",
      "transports": ["websocket", "sse"],
      "codecs": ["json", "protobuf"]
    }
  ],
  "next_cursor": "eyJpZCI6MTAyfQ=="
}
```

### 4.5. Eventos / Webhook para Lifecycle de Sala (Opcional / Futuro)

Cenário: um backend de matchmaking externo quer ser notificado quando uma sala muda para `DRAIN` ou quando uma nova sala se registra.

**Sugestão (v2):** Um mecanismo de webhook opcional onde o DNS notifica URLs externas sobre eventos de lifecycle (`room.registered`, `room.drain`, `room.expired`). Não é bloqueante para a v1, mas vale registrar como roadmap.

## 5. Considerações sobre a Relação com `room-protocol.md`

### 5.1. Referência cruzada dos perfis de segurança

O `discovery.md` não menciona os perfis de segurança (`strict_per_packet` vs `optimistic_session`) que são definidos no `room-protocol.md`. Como o Discovery já anuncia capacidades da sala no `GET /v1/rooms`, **seria valioso incluir o perfil de segurança da sala na listagem do DNS**, permitindo que o cliente de jogo saiba antecipadamente o perfil antes mesmo de resolver o endereço.

### 5.2. Alinhamento de endpoints entre documentos

O `desejo.md` (documento original) lista `POST /handshake` e `GET /schema` sem o prefixo `/v1/`. Já o `discovery.md` e `room-protocol.md` usam consistentemente `/v1/handshake` e `/v1/schema`. O `desejo.md` deveria ser atualizado para manter consistência.
